Курс створений для студентів 1–2 курсів ІТ-спеціальностей, які вже пишуть код, але потребують системної практики роботи з репозиторіями, гілками, конфліктами злиття та Pull Request у команді.

Очікувані результати навчання та умови завершення

  • Організовувати локальний репозиторій, фіксувати зміни та відсікати службові файли через .gitignore.
  • Застосовувати гілкування і злиття для паралельної розробки без втрати коду.
  • Діагностувати та коректно розв'язувати конфлікти злиття (merge conflicts).
  • Проводити командну взаємодію на GitHub: створювати Pull Request, давати конструктивний Code Review.

Умови зарахування: завершення всіх 3 модулів, участь у парному Code Review та набір не менше 60 балів зі 100 за підсумковою системою оцінювання.

Курс / Модуль 3. Онлайн-співпраця та ШІ-активність

Онлайн-взаємодія: парний практикум «Pull Request і Code Review»

Формат: асинхронна робота в парах у спільному GitHub-репозиторії (термін — 5 днів). Ролі: Автор змін (готує гілку й PR) та Рев'юер (перевіряє код і залишає аргументовані коментарі). Потім ролі змінюються.

  1. Учасник А створює гілку feature/calc-module, додає функцію з 2 навмисними недоліками та відкриває Pull Request.
  2. Учасник Б перевіряє PR у вкладці Files changed і залишає щонайменше 2 предметні коментарі (помилка логіки + стиль/читабельність).
  3. Учасник А вносить виправлення новим комітом у ту саму гілку і відповідає на кожен коментар.
  4. Учасник Б підтверджує зміни (Approve) і виконує Merge.

Зворотний зв'язок (2 способи): 1) взаємооцінювання за чеклістом нижче; 2) підсумковий коментар викладача до об'єднаного PR.

Інтерактивна картка взаємооцінювання Pull Request




Навчальна активність із підтримкою ШІ: «Розбір інциденту в історії Git»

Роль ШІ: спаринг-партнер для аналізу варіантів відновлення історії, який пояснює ризики команд (reset vs revert), але не виконує завдання замість студента.

Сценарій: розробник випадково закомітив і запушив у спільну гілку main помилкову конфігурацію. Використайте послідовність із 4 запитів до ШІ, перевірте його рекомендації за офіційною документацією git-scm.com і сформулюйте власне рішення:

  1. Уточнення проблеми: «Я запушив помилковий коміт у спільну гілку main, з якої вже працюють двоє колег. Які ризики виникнуть, якщо я використаю git reset --hard і git push --force?»
  2. Отримання варіантів: «Запропонуй 2 безпечні способи відкотити зміни в публічній гілці без перезапису спільної історії. Для кожного вкажи команду й результат у графі комітів.»
  3. Перевірка достовірності: «Наведи точні прапори команди git revert з офіційної документації Git для скасування merge-коміту та поясни параметр -m 1.»
  4. Самостійний висновок: на основі порівняння студент обирає стратегію для свого кейсу, перевіряє її на тестовому репозиторії та здає звіт із поясненням.
Правила доброчесності та безпеки: 1) Заборонено вводити у ШІ реальні токени, паролі, приватні ключі SSH або персональні дані; 2) Обов'язково вказати використаний ШІ-інструмент; 3) Кожну команду з відповіді ШІ перевірити за git help або git-scm.com.

Курс / Оцінювання, аналітика та персоналізована підтримка

Підсумкове завдання (адаптоване до умов використання ШІ)

Завдання: на базі власного навчального проєкту (будь-яка ваша лабораторна з програмування) створити GitHub-репозиторій, реалізувати 2 гілки, змоделювати й вирішити конфлікт злиття, оформити Pull Request із взаємним рев'ю, а також подати:

  • посилання на репозиторій з реальною історією комітів (git log --graph);
  • порівняння двох стратегій інтеграції (merge vs rebase) саме для вашої команди;
  • якщо використовувався ШІ — вказати інструмент, запит і те, що саме було перевірено чи виправлено власноруч;
  • коротку рефлексію (3–4 речення): яка помилка виникла під час роботи та як ви її виправили.
